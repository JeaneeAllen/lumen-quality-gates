# Lumen Quality Gates

A class demonstration of layered data quality gates for a fictional bank, Lumen.
All data is synthetic and generated by a seeded script.

> **Sample disclosure.** The report is a staging demonstration built from synthetic data:
> 5 fictional branches, 120 customers (99 of them own accounts), 200 accounts, and 30 days of
> end-of-day balances. It represents no real bank, customer, or branch network, and the
> five-branch sample is far too small to support conclusions about real deposit behaviour.
>
> **Evaluation date.** Every run uses the historical evaluation date **`2025-09-30`** (`--as-of`).
> The batch covers 2025-09-01 to 2025-09-30. A passing run shows the data is consistent with
> that fixed date. It does not show that any source system is delivering current data.

**Stack:** Python, CSV files, pytest, PyYAML, GitHub Actions, GitHub Pages.

## Data model

| File | Grain | Columns |
|---|---|---|
| `branches.csv` | one row per `branch_key` | `branch_key`, `branch_name`, `region` |
| `customers.csv` | one row per `customer_id` | `customer_id`, `customer_name`, `segment` |
| `accounts.csv` | one row per `account_id` | `account_id`, `customer_id`, `account_type`, `status`, `opened_date`, `branch_key`, `snapshot_date` |
| `daily_balances.csv` | one row per `account_id` and `balance_date` | `account_id`, `balance_date`, `balance` |

`daily_balances.csv` holds **end-of-day closing balances**, not deposit transactions.
Relationships: `accounts.customer_id → customers`, `accounts.branch_key → branches`,
`daily_balances.account_id → accounts`.

Clean data covers balance dates 2025-09-01 to 2025-09-30. Every `snapshot_date` is 2025-09-30.

```bash
python scripts/generate_data.py --seed 42 --out data --as-of 2025-09-30
python scripts/generate_data.py --seed 42 --out demo_data/<scenario> --scenario <scenario> --as-of 2025-09-30
```

The generator's `--as-of` is the last balance date and every `snapshot_date` (default `2025-09-30`).

| Scenario | One defect | Caught by |
|---|---|---|
| `schema_drift` | `account_type` renamed to `acct_type` | Layer 1, contract |
| `bad_type` | balance `12O.50` | Layer 2 |
| `missing_required` | blank `customer_id` | Layer 2, contract |
| `duplicate_account` | account row appended twice | Layer 3, contract |
| `duplicate_branch` | `BR-03` appended twice to branches | Layer 3 |
| `orphan_account` | balance row for `ACC-99999` | Layer 3, contract |
| `orphan_customer` | account owned by `CUS-99999` | Layer 3, contract |
| `invalid_status` | status `frozen` | contract |
| `stale_snapshot` | every `snapshot_date` 7 days old | contract (freshness) |
| `balance_spike` | +400% in one day | Layer 4 |
| `missing_day` | `ACC-00012` balance for 2025-09-10 deleted | Layer 4 (coverage) |

Every scenario except `missing_day` only modifies or appends rows. `missing_day` deletes one
row because missing source data is the defect it demonstrates.

## Quality layers

| Layer | Name | Checks |
|---|---|---|
| 1 | Schema | file exists and has rows; exact column set; every row has the right field count |
| 2 | Fields | required values not blank; `YYYY-MM-DD` dates; plain decimal numbers |
| 3 | Keys | unique `branch_key`, `customer_id`, `account_id`, `account_id + balance_date`; every reference resolves |
| 4 | Completeness & business rules | source coverage over the batch range; no day-over-day movement greater than 300% |
| 5 | Deposits mart | join keys unique before joining; after joining: mart grain, row-count preservation, balance-total reconciliation |

A layer runs only if all earlier layers passed; later layers are reported as SKIPPED.

**Batch range and coverage.** The batch is the 30 calendar days ending on `--as-of`
(`BATCH_DAYS` in `src/quality.py`). It comes from the explicit `--as-of`, never from dates found
in the data. For this synthetic baseline, **every account in `accounts.csv`, active or closed, is
expected to have exactly one closing balance on every date in the batch.** Coverage reports:
a missing interior, first, or last date; an account with no balance rows; and balance rows
outside the batch range.

**Coverage is not reconciliation.** Layer 4 coverage asks whether the *source* delivered every
expected balance. Layer 5 reconciliation asks whether the *join* lost or multiplied rows. A source
with a missing day joins perfectly and reconciles, so reconciliation alone can never prove the
source was complete.
Every failure names the file line. Records are never dropped, repaired, or deduplicated.
Allowed values (such as `status`) and freshness are enforced by the accounts contract.

**Balance movement rule.** For each account, a balance is compared only with the same
account's balance on the previous calendar day: `(today - yesterday) / abs(yesterday)`.
Movement strictly greater than 300% fails; exactly 300% passes. A move away from a zero
balance cannot be expressed as a percentage, so it fails; zero to zero passes.
Gaps are never bridged: a missing day is reported by its own check, and the days on
either side of it are not compared.

## Accounts contract

[`contracts/accounts.yaml`](contracts/accounts.yaml) defines, for `accounts.csv`:
field types, required values, patterns, uniqueness, allowed values (`status`: `active`, `closed`),
relationships (customers, branches, daily balances), freshness, the meaning of every field,
and a change policy.

```bash
python scripts/validate_contract.py --data data --as-of 2025-09-30
python scripts/validate_contract.py --data data --as-of 2025-09-30 --baseline <base commit's accounts.yaml>
```

| Exit | Meaning |
|---|---|
| 0 | Data meets the contract (and the change policy, if `--baseline` is given) |
| 1 | Data breaks the contract, or the contract change breaks the change policy |
| 2 | The contract file itself is missing or malformed |

### Freshness and the evaluation date

`snapshot_date` is the business date of the source-system state a row describes: the
account as of end of day on that date. It is set by the source extract, not by when the
file was copied, loaded, or validated.

`--as-of` is required and is **never derived from the data being validated**. Every row must
satisfy `as-of − 1 day ≤ snapshot_date ≤ as-of`.

**Evaluation date for this historical demonstration: `--as-of 2025-09-30`**, the last
balance date of the synthetic data. A pass at that date shows the extract is consistent
with that evaluation date. **It does not prove the source system is delivering current data.**
In production, `--as-of` would be the scheduled run date.

### Change policy

The version number describes a change; it does not approve one.

- **Non-breaking changes** (adding an optional field: MINOR; clarifying text: PATCH) are made
  in a pull request that increases the version.
- **Breaking changes are rejected by default**, even with a MAJOR version bump. Examples are a
  removed or renamed field, a type change, or an allowed value added or removed.
  They go through the consumer review process in `change_policy.consumer_review_process`:
  1. An issue describes the change and its impact.
  2. Every consumer owner records approval.
  3. The new rules are published as a separate contract file, for example `accounts_v2.yaml`.
  4. Consumers migrate.
  5. The old contract is retired in a later reviewed pull request.
- **Never edit the contract to make failing data pass.** Fix the data at the source.

`--baseline` must be the contract at a *different* commit. Stage 6 plan:
- **Pull requests** compare against the PR's base commit.
- **A push to `main`** compares against the commit before the push.

Comparing a contract with itself proves nothing.

## Running the gate

```bash
python scripts/run_gate.py --data data --as-of 2025-09-30
```

| Step | What happens |
|---|---|
| 1 | Delete `mart/deposits_mart.csv` and `mart/gate_result.json` from any earlier run |
| 2 | Accounts contract at `--as-of` |
| 3 | Quality layers 1–4 over the batch ending at `--as-of` |
| 4 | Layer 5 only if steps 2–3 passed: check join keys, build the mart, check grain, row count, totals |
| 5 | Pass: write the mart, then `gate_result.json` with `"status": "PASS"` and the mart's SHA-256. Fail: write `gate_result.json` with `"status": "FAIL"` and no mart |

**Deposits mart** (`mart/deposits_mart.csv`): one row per `account_id` and `balance_date`. Each
daily balance is joined to its account, customer, and branch. Columns: `account_id`,
`balance_date`, `balance`, `customer_id`, `customer_name`, `segment`, `account_type`, `status`,
`branch_key`, `branch_name`, `region`. Balances are copied as text and summed with `Decimal`, never
`float`.

| Exit | Meaning |
|---|---|
| 0 | Every check passed; the mart is published |
| 1 | A contract or quality check failed; no mart exists in `mart/` |
| 2 | The contract file is invalid; no mart exists in `mart/` |

Because step 1 runs first, a failed run never leaves an earlier mart looking current.
Only a mart whose `gate_result.json` says `PASS` and whose SHA-256 matches may be published.
The terminal shows the first 10 failures per check; `gate_result.json` has all of them.

## Staging deposits report

```bash
python scripts/run_gate.py --data data --as-of 2025-09-30
python scripts/build_report.py --mart-dir mart --out site --release-label release_label.txt
```

The three `build_report.py` arguments shown are the defaults. Output: `site/index.html` and `site/report.json`.

**Evidence required before anything is written.** The script first deletes `site/index.html` and
`site/report.json`. It then needs all of the following, or it exits 1 with `REPORT REJECTED` and
writes nothing:

- `mart/gate_result.json` exists, is valid JSON, has `"status": "PASS"` and the expected fields
- `mart/deposits_mart.csv` exists and its SHA-256 matches the hash the gate recorded
- the mart's columns and row count match, and its latest `balance_date` equals the gate's batch end
- `release_label.txt` contains exactly one non-blank line

The report reads only the validated mart. It never re-reads source files, rebuilds joins, or repairs data.

**What the page shows.**
- The notice "Lumen staging demonstration — synthetic data."
- The release label
- The evaluation date (`as_of`), batch range, and latest balance date
- Contract version, source commit, and mart SHA-256
- Branch, customer, and account counts: distinct values in the mart. Customers without accounts are not in the mart; the clean data has 120 customers, 99 of them with accounts.
- Latest-day total balance, latest-day average customer balance, and branch summaries

**Latest-day method.**
1. Use only rows for the latest balance date. The 30 daily snapshots are **not** summed: they
   are 30 end-of-day positions of the same money, not 30 separate amounts.
2. Sum each customer's account balances.
3. Average those customer totals. Averaging per account would understate customers who hold
   several accounts.

**Rounding.** All arithmetic uses `Decimal`. Totals are exact, because balances are already in cents.
Averages are rounded to the cent with `ROUND_HALF_UP`.

**Customers in several branches.** The generator picks each account's `customer_id` and
`branch_key` independently. In the clean data, 49 of 99 customers hold accounts at more than one
branch. A branch summary counts a customer at every branch where they hold an account, using
only their balances at that branch. Branch totals therefore add up to the overall total, but
branch customer counts add up to more than 99 (166 in the clean data).

**Source commit.** `GITHUB_SHA` in CI; otherwise local `git rev-parse HEAD`, marked
"(with uncommitted changes)" when the working tree is dirty; otherwise "unavailable".

## CI and GitHub Pages

Workflow: [`.github/workflows/quality-gates.yml`](.github/workflows/quality-gates.yml).
It runs on **every pull request targeting `main`** and **every push to `main`**, with no path filters.

### Job `quality-gate` (required check name: `quality-gate`)

| Step | Command |
|---|---|
| Check out, set up Python 3.12 (same as local), install | `python -m pip install -r requirements.txt` |
| Full test suite | `python -m pytest -v` |
| Clean synthetic data | `python scripts/generate_data.py --seed 42 --out data --as-of "$AS_OF"` |
| Contract compatibility | `python scripts/validate_contract.py --contract contracts/accounts.yaml --data data --as-of "$AS_OF" --baseline <baseline>` |
| Dataset gate | `python scripts/run_gate.py --data data --as-of "$AS_OF" --out mart --contract contracts/accounts.yaml` |
| Report | `python scripts/build_report.py --mart-dir mart --out site --release-label release_label.txt` |
| Push to `main` only | `configure-pages`, then upload `site/` as the Pages artifact |

`AS_OF` is set once, to `2025-09-30`, at the top of the workflow. Any non-zero exit fails the job.
No step uses `continue-on-error`, and a failure stops every later step, so nothing is uploaded.

**Contract baseline.**

| Event | Baseline | If it can't be used |
|---|---|---|
| Pull request | contract at `github.event.pull_request.base.sha` | job fails: no SHA, fetch failed, or contract missing at that commit |
| Push to `main` | contract at `github.event.before` (main before the push) | same |
| First push to `main` | none: `before` is all zeros | **bootstrap**: notice logged, compatibility skipped for that push only |

The baseline commit is fetched explicitly with `git fetch --depth=1 origin <sha>`. The job refuses
a baseline equal to the commit under test, so it never compares the contract with itself.

**Bootstrap.** The very first push to `main` has no earlier commit, so there is nothing to compare
against. The workflow logs a `Contract bootstrap` notice and runs every other check as normal.
That first push must already contain `contracts/accounts.yaml`. If an earlier commit on `main`
lacks the contract, the next run fails with `Missing baseline contract`, which is intended.

### Job `deploy` (push to `main` only)

Runs only after `quality-gate` succeeds (`needs: quality-gate`). It deploys the already-uploaded
validated `site/` artifact with `actions/deploy-pages`. It never checks out code or regenerates data.
It uses the `github-pages` environment, and `concurrency: github-pages` with
`cancel-in-progress: false`: only one deployment runs at a time, and a queued older run is replaced by
a newer one, so an older build cannot overwrite a newer one.

### Permissions

| Scope | Permission | Why |
|---|---|---|
| Workflow default | `contents: read` | Least privilege for any job that doesn't override it |
| `quality-gate` | `contents: read` | Check out code and fetch the baseline commit |
| `quality-gate` | `pages: read` | `configure-pages` reads the Pages settings (push to `main` only) |
| `deploy` | `pages: write` | Publish the artifact to GitHub Pages |
| `deploy` | `id-token: write` | OIDC token that proves the deployment came from this workflow run |

No job can write to the repository contents.

Actions used: `actions/checkout@v7`, `actions/setup-python@v7`, `actions/configure-pages@v6`,
`actions/upload-pages-artifact@v5`, `actions/deploy-pages@v5`. These were the latest official
major versions when this was written.

### Repository settings (manual)

1. **Pages source.** Settings → Pages → Build and deployment → Source: **GitHub Actions**.
2. **`github-pages` environment.** Created automatically by the first deployment. In Settings →
   Environments → `github-pages` → Deployment branches and tags, keep it limited to `main`.
3. **Branch protection for `main`.** Settings → Branches → Add classic branch protection rule
   (or an equivalent ruleset) for `main`:
   - Require a pull request before merging.
   - Require status checks to pass before merging, with **`quality-gate`** as a required check.
     It appears in the search box only after the workflow has run once; the bootstrap push does that.
   - Require branches to be up to date before merging, so the check runs against current `main`.
   - Do not allow bypassing the above settings (include administrators).
   - Block force pushes and deletions. A force push can make the pre-push baseline unfetchable.
   - Do **not** make `deploy` a required check: it never runs on pull requests.
4. **Actions permissions.** Settings → Actions → General: allow GitHub Actions and the
   `actions/*` actions. The workflow sets its own token permissions, so the default
   "Read repository contents" workflow permission is enough.

### Capturing pull request evidence

Save the results in `evidence/` (committed). Example with the GitHub CLI:

```bash
# Failing PR: a breaking contract change (adds 'frozen' and bumps to 2.0.0)
git switch -c demo/breaking-contract
sed -i '' -e 's/allowed: \[active, closed\]/allowed: [active, closed, frozen]/' \
          -e 's/^version: "1.0.0"/version: "2.0.0"/' contracts/accounts.yaml
git commit -am "Demo: breaking contract change (expected to fail)"
git push -u origin demo/breaking-contract
gh pr create --base main --title "Demo: breaking contract change" --body "Expected to fail quality-gate."
gh pr checks --watch                       # waits; ends with quality-gate fail
gh run view --log-failed > evidence/pr_fail_breaking_contract.txt
# Screenshot the PR's Checks section and the blocked merge button: evidence/pr_fail_breaking_contract.png
gh pr close --delete-branch

# Passing PR: a harmless change
git switch main && git switch -c demo/passing-change
echo "- Demo pull request." >> docs/ai_session_notes.md
git commit -am "Demo: harmless change (expected to pass)"
git push -u origin demo/passing-change
gh pr create --base main --title "Demo: passing change" --body "Expected to pass quality-gate."
gh pr checks --watch
gh run view --log > evidence/pr_pass.txt
# Screenshot the green check and the enabled merge button: evidence/pr_pass.png
```

In the failing run's log, look for `CONTRACT FAILED` and
`breaking changes are rejected by default` in the **Contract compatibility** step. Every later
step should show as skipped.
